Executive Summary

The Municipal Fisheries Office manages coastal monitoring and enforcement activities using paper forms, ad hoc spreadsheets, and chat groups. These practices make it difficult to track fishing activities, detect protected area violations, and consolidate catch data for decision-making. The proposed Coastal Fisheries Monitoring and Enforcement Information System is a web-based platform enabling fishers to record catches and locations, and enabling administrators and inspectors to monitor tracks, manage protected zones, receive real-time alerts, and analyze activity logs.

Based on analysis of the client’s environment and the system prototype implemented with Node.js, Express, and a lightweight JSON datastore, the project is technically feasible for initial deployment, economically reasonable for an academic capstone with minimal infrastructure costs, and operationally feasible given existing roles and processes. A phased timeline of 10–12 weeks is recommended, with a plan to migrate storage to a durable database post-capstone. The overall recommendation is to proceed.

Introduction

Background of the Client. The Municipal Fisheries Office is responsible for coastal resource management, licensing, and enforcement. Staff coordinate with barangay officials and fishers to monitor activities, document catches, and ensure compliance with protected area rules.

Current System or Process. Data collection relies on manual logs, spreadsheets, and messaging apps. Location tracking and zone enforcement are reactive, with limited geospatial analysis and delayed reporting.

Problem Statement. The office needs a unified system to capture geolocated catches, track vessel movement, detect protected area violations, and streamline reporting. Manual processes lead to inconsistent data quality, slow consolidation, and limited visibility.

Objectives of the Feasibility Study. Determine the technical, economic, operational, and schedule feasibility of implementing a web-based monitoring and enforcement system aligned with capstone requirements.

Project Description (Proposed Information System)

Proposed System Overview. A web-based platform with role-based access (admin, inspector, fisher, researcher). Core features include user registration and authentication, geolocated catch submission, GPS track logging, protected zone management (GeoJSON), automated alerts on zone approach/violation, push notifications (VAPID), data export (GeoJSON/CSV), and activity logging.

Scope and Limitations. Scope covers catch and track recording, protected zone management, alerts, user management, and public exports. Out of scope for the capstone are payments, licensing workflows, and long-term archival. Initial storage uses JSON files suitable for prototype; production should migrate to a durable database.

Target Users. Fishers (data entry for catches and optional tracks), inspectors (live monitoring and alerts), administrators (user/zone management, analytics), and researchers (read-only data exports).

Feasibility Analysis

Technical Feasibility.

  • Technology stack: Node.js, Express, JSON storage (Lowdb), web-push, Mapbox integration, file uploads with EXIF GPS parsing, Turf.js for geospatial checks.
  • Deployment options: Local LGU server or serverless hosting. Static assets are served from the built-in web server; APIs expose JSON and streaming endpoints.
  • Capabilities: Role-based JWT auth, file uploads, geospatial analysis, push notifications, CSV/GeoJSON export, SSE for live monitoring.
  • Risks: GPS accuracy, intermittent connectivity, ephemeral storage on serverless platforms, and potential scaling limits of JSON storage. Mitigation: migrate to PostgreSQL or MongoDB, add offline caching, and enforce input validation.

Economic Feasibility.

  • Estimated costs: hosting (entry-tier), domain, SSL (often bundled), minimal hardware for local deployments, training time.
  • Benefits: faster data consolidation, improved enforcement, reduced manual errors, near real-time alerts, and better reporting for policy decisions.
  • Conclusion: For a capstone and pilot, costs are low and benefits significant, supporting a positive cost-benefit outlook.

Operational Feasibility.

  • Readiness: Existing roles fit the system design; staff can adopt dashboards with brief training.
  • User acceptance: Interfaces for fishers and admins are simple; data exports integrate with existing reporting.
  • Change management: Provide onboarding sessions, quick guides, and feedback loops to refine workflows.

Schedule Feasibility.

  • Weeks 1–2: Requirements finalization and data gathering.
  • Weeks 3–5: Core API and data model implementation; auth and uploads.
  • Weeks 6–7: Geospatial features, zones, alerts, push notifications.
  • Weeks 8–9: Admin dashboards, exports, activity logging, QA.
  • Weeks 10–12: Pilot, user training, documentation, final adjustments.

Conclusion and Recommendation

The proposed system is feasible within the capstone timeframe and resources. It addresses key pain points in monitoring and enforcement, introduces geospatial awareness, and delivers practical reporting. Proceed with phased deployment, plan for database migration post-capstone, and codify operational policies for sustainable use.
